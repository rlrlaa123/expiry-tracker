# 비식품 유통기한 트래커 — v1 기능 스펙 (확정)

> 최종 확정일: 2026-06-10
> 한 줄 정의: 비식품 생활용품(화장품·의약품·조미료·생활화학제품)의 사용기한을 사진 한 장으로 등록하고, 만료 전에 알려주는 개인용 트래커.
> 핵심 원칙: **등록 10초, 알림 하루 1회. 유저 0명일 때도 가치 있을 것.**

---

## 0. 제품 정의

- 타겟: 1인 가구 ~ 가정 살림 관리자. 첫 사용자는 개발자 본인이어도 완결된 효용이 있는 single-player 구조
- 포지셔닝: 식품/냉장고 관리 앱과 경쟁하지 않음. "작년에 산 선크림 아직 써도 되나?"를 해결하는 **비식품 전용**
- 운영 형태: 비로그인, 로컬 저장 우선. 계정/클라우드 백업 없음 (v1.1에서 선택형 백업 검토)

## 1. 품목 등록

### 1-1. 등록 진입점: 카메라 단일

- 홈의 등록 버튼(FAB)은 **카메라 하나**. 별도의 "수동 등록" 메뉴 없음
- 카메라 촬영 또는 갤러리 선택 → 비전 AI가 품목명 / 브랜드 / 카테고리 / 기한 표기 추출
- AI 처리 목표: 3초 이내
- 사진은 압축 저장하여 품목 썸네일로 사용

### 1-2. 확인/편집 폼 (수동 입력 겸용)

- 인식 결과 확인 화면이 곧 수동 편집 화면. 별도 화면 없음
  - **인식 성공**: 채워진 폼 → 확인 후 저장
  - **부분 성공** (제조번호만 있는 화장품 등 기한 미표기 제품): 품목명·카테고리만 채우고, 기한은 카테고리별 PAO 기본값을 제안
  - **완전 실패** (라벨 없음, 사진 흐림): 같은 화면이 빈 폼으로 열림 — 에러 팝업 금지, 자연스러운 폴백
- AI 신뢰도가 낮은 필드는 비워두고 입력 유도
- 자주 등록하는 품목은 최근 등록 템플릿으로 원탭 재사용

### 1-3. 오프라인 동작

- AI 호출 불가 시 빈 폼 폴백으로 처리 (v1 확정)
- 사진 대기열 + 온라인 복귀 시 자동 인식은 백로그(v1.1+)

## 2. 날짜 체계 (핵심 도메인 로직)

다루는 날짜 3종: **유통기한(EXP), 제조일(MFG), 개봉일**

만료일 계산 우선순위:

1. 유통기한 표기가 있으면 그대로 사용
2. 제조일만 있으면 카테고리별 기본 보존기간 적용
3. 개봉일이 기록되면 `만료일 = min(유통기한, 개봉일 + PAO)` 로 재계산

### PAO(개봉 후 사용기한) 기본값 테이블 (내장, 품목별 덮어쓰기 가능)

| 카테고리 | 기본 PAO |
|---|---|
| 선크림 | 12개월 |
| 마스카라 | 6개월 |
| 립 제품 | 12개월 |
| 연고 | 6개월 |
| 안약 | 1개월 |
| 참기름 등 유지류 | 6개월 |

※ 출시 전 카테고리 전체에 대해 기본값 테이블 확장 필요

### 개봉 처리

- 목록/상세에서 "개봉" 버튼 원탭 → 개봉일 자동 기록 + 만료일 재계산
- 식품 앱과의 결정적 차별점이므로 UI에서 가장 접근하기 쉬운 위치에 배치

## 3. 데이터 모델

품목(Item):

```
id, 품목명, 브랜드, 카테고리_id, 썸네일,
EXP(유통기한), MFG(제조일), 개봉일, PAO,
계산된 만료일,
상태(개봉전 / 사용중 / 만료 / 소진 / 폐기),
보관 위치(옵션), 메모, 생성일, 수정일
```

카테고리(Category):

```
id, 이름, PAO 기본값(개월, nullable),
보존기간 기본값(개월, nullable),
기본 제공 여부(builtin: true → 삭제 불가)
```

## 4. 알림

- **하루 1회 묶음 알림** 고정 (기본 오전 9시, 시각 변경 가능). 개별 푸시 남발 금지
- 트리거: D-30 / D-7 / D-1 / 만료일. 단계별 on/off 가능
- 알림 탭 → 만료 임박 목록 직행
- 만료 품목에는 처리 유도 액션 제공: **폐기 / 아직 사용 / 기한 연장**

## 5. 목록·조회

- 기본 정렬: 만료 임박순
- 상태 뱃지 색상: 만료(빨강), D-7(주황), D-30(노랑), 안전(초록)
- 필터: 카테고리, 상태, 보관 위치 / 검색: 품목명
- 홈 상단에 "만료 임박 Top 5" 카드

## 6. 상태 관리·아카이브

- 소진/폐기 처리 시 아카이브로 이동 (메인 목록 오염 방지)
- 아카이브에서 **"다시 샀어요" 원탭 재등록** — 기한만 새로 입력하면 완료
  - 재구매 사이클이 긴 비식품 특성상 리텐션의 핵심 장치

## 7. 설정

- 알림 시각, 알림 단계(D-30/D-7/D-1/만료일) on/off
- 카테고리별 PAO 기본값 편집
- **커스텀 카테고리 추가/삭제**

### 7-1. 커스텀 카테고리

- 추가 항목: 이름(필수), PAO 기본값(선택 — 미설정 시 PAO 계산 미적용), 보존기간 기본값(선택)
- 추가 진입점 2곳, 동일한 시트 재사용:
  1. 확인/편집 폼의 카테고리 칩 끝 "＋"
  2. 설정 > PAO 기본값 테이블 하단 "＋ 새 카테고리"
- **AI 인식 연동**: 비전 프롬프트에 사용자 카테고리 목록을 동적으로 주입하여 커스텀 카테고리로도 자동 분류. 매칭 실패 시 "기타"로 분류
- 삭제 규칙: 기본 제공 카테고리는 삭제 불가(PAO 값 편집만 가능), 커스텀 카테고리 삭제 시 소속 품목은 "기타"로 이동 (품목 데이터는 보존)

## 9. 비기능 요구사항

- 등록 완료까지 10초 이내 (촬영 → 저장)
- AI 인식 외 모든 기능(조회·편집·상태 변경)은 오프라인 동작
- 알림은 OS 로컬 알림 기반 (서버 푸시 불필요 — 로컬 우선 구조와 일치)

## 10. 기술 스택 (확정)

### 앱

- **Expo (React Native + TypeScript)**
  - 카메라: expo-camera / expo-image-picker, 이미지 압축: expo-image-manipulator
  - 로컬 알림: expo-notifications
  - DB: expo-sqlite + Drizzle ORM (Item / Category 테이블)
  - 상태 관리: Zustand
  - 빌드/배포: EAS Build + EAS Update(OTA)
- 차선 검토안: Capacitor + Vue 3 (착수 속도 우위, 플러그인 안정성 열위로 보류)
- PWA 제외: iOS에서 예약 로컬 알림 불가 → 핵심 기능 불성립

### AI 인식 아키텍처 (하이브리드)

```
사진 촬영
  ├─ [1차·온디바이스] ML Kit 텍스트 인식 (무료·오프라인)
  │    → 날짜 패턴 정규식 파싱 (EXP/제조/까지 등) → 기한 추출
  └─ [2차·온라인] Gemini 무료 티어 (Flash-Lite)
       → 품목명 정제 + 카테고리 분류 (사용자 카테고리 목록 프롬프트 주입)
```

- **API 프록시**: Cloudflare Workers 무료 티어에 단일 엔드포인트(이미지 → 인식 JSON). API 키는 프록시에만 보관, 기기 ID 기반 rate limit. 서버는 데이터 미저장 → 로컬 우선 원칙 유지
- **무료 티어 전제 조건 (인지된 리스크)**:
  - 무료 티어 입력은 모델 학습에 사용될 수 있음 → 개인정보 안내문에 "사진은 인식 목적으로 외부 AI에 전송될 수 있음" 명시
  - 쿼터는 예고 없이 변동 가능 (2025-12 축소 전례) → 한도 도달 시 유료 전환 또는 OCR-only 폴백
- **오프라인 동작 개선**: 네트워크 없어도 ML Kit OCR로 기한은 자동 추출, 품목명만 수동 입력 (기존 "빈 폼 폴백"보다 상향)

### 알림 스케줄링 전략

- 로컬 알림은 예약 시점에 내용이 고정됨 → **"다음 1회 묶음 알림"만 예약**하고, 데이터 변경·앱 실행 시마다 내용 재계산 후 재예약
- iOS 대기 알림 64개 제한 자연 회피

## 11. 비전 AI 인식 설계

### 응답 JSON 스키마

```json
{
  "product_name": "string | null",
  "brand": "string | null",
  "category": "string | null",
  "dates": [
    { "type": "EXP | MFG | UNKNOWN",
      "value": "YYYY-MM-DD | YYYY-MM",
      "raw": "라벨 원문 표기" }
  ],
  "confidence": {
    "product_name": "high | low",
    "brand": "high | low",
    "category": "high | low",
    "dates": "high | low"
  }
}
```

설계 결정:
- **dates 배열**: 라벨에 제조일·유통기한 혼재 → 전부 분류시키고 채택은 클라이언트
- **raw 원문 보존**: 폼에서 인식 근거 표시("라벨의 '...'를 유통기한으로 읽었어요") + 디버깅
- **confidence 이진(high/low)**: 소형 모델의 수치 캘리브레이션 불신 → UI(노란 테두리) 직결
- **모르면 null**: 환각 방지를 프롬프트에서 반복 강조

### 프롬프트 (프록시에서 조립)

```
생활용품 라벨 사진과 OCR 텍스트입니다. JSON만 출력하세요.

규칙:
1. product_name: 핵심 제품명만. 용량·광고문구 제외. 확신 없으면 null
2. brand: 브랜드명. 없으면 null
3. category: 다음 중에서만 선택: [{사용자_카테고리_목록}, 기타]
4. dates: 발견한 모든 날짜를 분류:
   - EXP: "까지", "유통기한", "사용기한", EXP, BBE 문맥
   - MFG: "제조", MFG, 제조번호 옆 날짜
   - UNKNOWN: 구분 불가
   value는 YYYY-MM-DD 또는 YYYY-MM, raw는 라벨 원문 그대로
5. confidence: 필드별 "high"/"low". 추측이 섞이면 무조건 "low"
6. 보이지 않는 정보를 지어내지 마세요. 모르면 null

OCR 텍스트: {ML_Kit_결과}
```

- ML Kit OCR 결과를 프롬프트에 동봉 → 소형 모델의 시각 부담을 텍스트로 보조, 정확도 상승
- 이미지는 장변 1024px·JPEG 압축 후 전송 (토큰/비용 절감)

### 클라이언트 후처리 규칙 (LLM 방어선)

1. JSON 파싱 실패 → 코드펜스 제거 후 1회 재파싱 → 실패 시 OCR-only 결과로 폼 오픈
2. dates 채택 순서: EXP 우선 → MFG만 있으면 보존기간 가산(2장 규칙) → UNKNOWN 단일이면 EXP 가정 + low 처리
3. `YYYY-MM`은 해당 월 말일로 해석 (화장품 "2027.03까지" 관례)
4. category가 목록 밖 값 → "기타" 강제 (모델 일탈 방어)
5. EXP가 과거 날짜 → 그대로 표시 + "이미 만료된 제품이에요" 안내

### 프록시 API

- `POST /recognize` — 입력: `{ image(base64), ocr_text, categories[], device_id }`
- Rate limit: device_id당 분당 5회 / 일 50회
- 응답: 위 스키마 JSON 또는 `{ error }`
- 서버 측 데이터 저장 없음 (로컬 우선 원칙)

## 확정 결정 로그

| 결정 | 선택 | 근거 |
|---|---|---|
| 저장 방식 | 로컬 우선, 비로그인 | 진입 마찰 제거가 백업 요구보다 우선 |
| 바코드 | 제외 | 비식품 바코드 DB 적중률 낮음, 사진 인식이 범용적 |
| 등록 진입점 | 카메라 단일 | "사진 찍으면 끝" 정체성 강화, 화면 수 절감 |
| 기한 미표기 제품 | 부분 성공 처리 | 인식 실패가 아니라 PAO 기본값 제안으로 연결 |
| 오프라인 | OCR로 기한 추출 + 품목명 수동 | ML Kit 도입으로 "빈 폼 폴백"에서 상향 |
| 카테고리 | 사용자 정의 엔티티 | PAO 계산 키, AI 프롬프트 동적 주입으로 자동 분류 유지 |
| 앱 스택 | Expo (RN + TS) | 1st-party 카메라·알림·OTA, 플러그인 리스크 최소 |
| 비전 모델 | Gemini 무료 티어 (Flash-Lite) | 비용 0원 시작, 학습 사용·쿼터 변동 리스크 인지 후 수용 |
| 인식 구조 | ML Kit OCR + LLM 하이브리드 | API 의존 절반 축소, 오프라인 경험 상향 |
| API 키 보호 | Cloudflare Workers 프록시 | 키 비노출, rate limit, 데이터 미저장 |
